Benefits

A map of the service you can check, not a summary you have to trust

Evidence on every claim

Each node and edge carries a file and line range. Evidence that does not exist in the code is dropped before it reaches the doc.

A Verifier that never sees your code

It compares the generated doc with your own requirements docs and reports contradictions, doc only items and code only gaps. Every quote is string checked.

Read only and local

It works on a copy of your source. Secrets are redacted at ingest, and the review server listens on 127.0.0.1 behind a token.

A hard budget and cheap re runs

Set --max-usd to stop a run gracefully. An incremental re run of unchanged code makes zero model calls.

Bring your own model

Any provider LiteLLM supports, set per task. Sample configs for Gemini and Anthropic are included, and a custom endpoint is one setting.

A review loop that stays small

Comment on an item or resolve a finding, and only the code around that node is re analyzed. A changelog records what changed and why.

Every claim points to a line of code. Every document is checked against the code. Nothing leaves your machine except the model call you configure.

How it works

Three steps from source folder to reviewed doc

01

Ingest and extract

Copy the source into the project, redact secrets, then pull static facts: routes, config keys, dependencies and file to file imports.

migration-agent init ./service
migration-agent ingest service.migration
migration-agent extract service.migration
02

Analyze

The model reads chunks of code and returns nodes, edges and business rules. Each one is checked against the real file and line, and coverage is reported.

migration-agent analyze service.migration \
  --config gemini.config.json --max-usd 1
03

Verify and review

Drop your requirements into the project, run the Verifier, then resolve findings in the local review page. Only the touched nodes are re analyzed.

migration-agent verify service.migration
migration-agent review service.migration
migration-agent resolve service.migration F-0001

Quickstart

Run it on your own service in about five minutes

Needs Python 3.12 and an API key for the model you choose. Put the key in a .env file in the project root, never on the command line.

terminal
# get the source: {{repository url}}
uv pip install -e ".[llm]"
echo "GEMINI_API_KEY=your key here" > .env

migration-agent init ./my-service
migration-agent ingest my-service.migration
migration-agent extract my-service.migration
migration-agent analyze my-service.migration --dry-run   # estimate first
migration-agent analyze my-service.migration --config gemini.config.json --max-usd 1
migration-agent review my-service.migration

FAQ

Questions before you try it

Does it change my code?

No. Ingest copies your source into a project folder, and every later step reads that copy only. Archives and git sources are validated for path traversal, symlink escapes and decompression bombs.

Which languages and frameworks does it understand?

Static extraction covers Python, JavaScript, TypeScript and Java files. Route extractors cover Express, Spring, Flask, FastAPI, Rails, ASP.NET and Django. Schema extractors cover Flyway, Alembic, Prisma and TypeORM, and OpenAPI and proto files are parsed. The model fills in everything else.

Which models can I use?

Any provider LiteLLM supports, chosen per task in a config file or with MA_* environment variables. We have run it with Gemini models. Sample configs for Anthropic models are included but we have not run them.

What does a run cost?

Run analyze --dry-run for an estimate before spending anything. On the 18 file Express sample the plan estimated $0.01. --max-usd is a hard stop, and a run that reaches it keeps its partial results.

What happens to secrets in my repo?

Ingest redacts credential patterns and withholds key and environment files before anything reaches a prompt, a cache or a document. Redaction is pattern based, so unusual secrets can still slip through. The threat model lists this as a known risk.

Does anything leave my machine?

Only the calls to the model endpoint you configure, plus a git clone if your source is a git URL. The offline commands open no outside connections, and the review server binds to 127.0.0.1 with a per run token.

Can it handle a large repository?

Chunk planning handled a synthetic 2,420 file repo in about a tenth of a second in our tests, and incremental runs re analyze only changed files and their direct importers. We have not run a model over a repo that size yet.
