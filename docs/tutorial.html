migration-agent

Read a legacy codebase without ever running it. Get an evidence-backed understanding document, a knowledge graph, and a blind check against your own docs.

On this page What it is Install and set up Walkthrough The review loop Docker, safety, help

1What it is

Every claim the tool makes cites a file, line range and a verbatim quote from your code, so you can check it. A second, blind Verifier then compares that document against your existing documentation, without seeing how the document was built, and flags where the two disagree. You review those disagreements in a local web UI.

Read-onlyIt never executes or modifies the analysed code. Model access is limited to path-jailed read-only tools.
Secrets withheldCredentials are withheld or redacted at ingest.
One folder of stateEverything lives in a single <name>.migration folder.
Bounded cost--max-usd caps spend; results are cached and runs resumable.

2Install and set up

You need Python 3.11 or newer and one model API key. Everything except the analysis and verify steps works without a key.

python -m venv .venv && . .venv/bin/activate
pip install ".[llm]"        # the [llm] extra adds LiteLLM for real model calls
migration-agent --version   # migration-agent, version 0.2.0

For development: pip install -e ".[dev,llm]" then PYTHONPATH=src python -m pytest -q (576 tests pass).

API keys

Copy .env.example to .env and fill in a key. The CLI loads it at start-up and never overrides variables already set in your shell. .env is git-ignored; never commit it.

VariableProvider
ANTHROPIC_API_KEYClaude models
GEMINI_API_KEY (or GOOGLE_API_KEY)Gemini models
OPENAI_API_KEYOpenAI models
No key yet? Run analyze --offline to try the whole pipeline with a stand-in model.

Choosing models

The repo ships gemini.config.json, gemini-flash3.config.json and gemini-lite.config.json. Each maps five tasks (chunk_extract, cross_ref, business_rules, gap_fill, verifier) to a model and sets prices, retries and backoff. Pass one with --config.

For containers and CI, MA_* variables override the file. Precedence, lowest to highest: built-in defaults, the MA_LLM_CONFIG file, then MA_* variables. An explicit CLI flag wins over all of them.

VariableEffect
MA_LLM_CONFIGPath to a base config.json
MA_LLM_MODELDefault model
MA_LLM_MODEL_<TASK>Model for one task, e.g. MA_LLM_MODEL_VERIFIER
MA_LLM_API_BASECustom endpoint (proxy, Azure, Bedrock gateway)
MA_LLM_MAX_RETRIES, MA_LLM_TIMEOUT, MA_LLM_MAX_OUTPUT_TOKENSRetry and size limits
MA_LLM_BACKOFF_BASE, MA_LLM_BACKOFF_MAXRetry backoff in seconds
MA_LLM_PRICE_DEFAULTFallback price as "in,out" USD per 1M tokens
MA_MAX_USDHard budget, same as --max-usd
MA_LOG_LEVELDEBUG, INFO, WARNING, ERROR or CRITICAL

3Walkthrough

Every command takes the project folder as its first argument and appends to audit/audit.jsonl. Run migration-agent COMMAND --help for the authoritative option list.

Step 1. Create the project

migration-agent init ./legacy-orders
# or a zip, tarball or git URL, with a custom location and name:
migration-agent init https://example.com/team/orders.git --project ./orders.migration --name "Orders service"

Nothing is copied yet. The repo includes three sample projects to practise on: django-lite.migration, express-crud.migration and spring-lite.migration.

Step 2. Ingest the code

migration-agent ingest legacy-orders.migration

Copies the source into code/ with limits: 500 MB, 200,000 files, a compression-ratio cap of 100, git clones with hooks disabled. It skips symlinks, binaries, files over 1 MB and vendor or build folders (.git, node_modules, vendor, build, dist, target, virtualenvs). Credential files such as .env, *.pem, id_rsa and .npmrc are withheld entirely; secrets in other files become [REDACTED:<kind>]. Read ingest_report.json to see what was kept. If the source changes later, run ingest --refresh.

Step 3. Extract static facts

migration-agent extract legacy-orders.migration

No model involved. tree-sitter pulls out AST facts, dependency manifests, configuration keys, routes and import edges into facts/, and writes inventory.json: the checklist of everything the analysis must account for.

Step 4. Plan, then analyze

migration-agent analyze legacy-orders.migration --dry-run          # plan + cost estimate, no key needed
migration-agent analyze legacy-orders.migration --config gemini.config.json --max-usd 3

Always dry-run first. The real run chunks the code, extracts per chunk with the model, merges, resolves cross-references, verifies each piece of evidence against code/, runs a business-rules pass and fills gaps for unmapped inventory items. It writes docs/understanding.latest.md, docs/graph.html and a new graph snapshot.

OptionUse it to
--dry-runPrint the plan and estimated cost, then exit
--max-usd NHard budget; stops gracefully and a re-run continues without paying twice
--config FILEPick models and prices
--workers NRun N chunk calls in parallel; merge order stays deterministic
--incrementalAfter ingest --refresh, re-analyse only changed chunks and dependents; IDs stay stable
--offlineNo model; a facts-level result, not a real analysis

render PROJECT builds a facts-only graph and document with no model, handy for checking extraction.

Step 5. Verify against your own docs

Put your existing docs (.md, .txt, .html, .docx, .pdf) in user_docs/, then:

migration-agent verify legacy-orders.migration --config gemini.config.json --max-usd 1

The Verifier sees only the generated document and your docs, never the code, and the analysis never saw your docs. That separation is why a disagreement means something. Each finding quotes both sides verbatim; findings whose quotes cannot be string-matched are dropped. Results go to feedback/findings.json.

Finding kindMeaning
contradictionThe docs and the code-derived document disagree
doc_onlyDocumented, but not found in the code
code_onlyIn the code, but undocumented
doc_vs_docYour own docs disagree with each other

Step 6. Review

migration-agent review legacy-orders.migration

Starts the local review UI and prints a URL with a one-time token. See the next section.

4The review loop

Each disagreement becomes a recorded decision and, where needed, a targeted re-analysis, producing a new graph version and a changelog entry.

The review UI

migration-agent review legacy-orders.migration --port 8765 --no-browser

It prints a URL like http://127.0.0.1:8765/<token>/. The UI shows the understanding document with coverage and confidence, the findings, graph versions and diffs. You can comment on any graph item and resolve findings.

  • Binds to 127.0.0.1 only; do not forward the port.
  • Every request needs an unguessable token, and the Host header is validated.
  • Cross-origin POSTs are rejected; bodies are capped at 64 KB and texts at 5,000 characters.
  • It can only write comments and resolutions, and cannot run inside a container.

Resolving from the command line

migration-agent resolve orders.migration F-0001 --status accepted_doc --note "Discount is 25% from 10 items"
migration-agent resolve orders.migration --comment RULE-0003 --note "Check the VIP exception in pricing.py"
migration-agent resolve orders.migration F-0004 --status dismissed --no-reanalyze
StatusMeaningRe-analysis
accepted_docYour documentation is right; the code-derived claim is wrongYes, affected nodes
accepted_codeThe code is the truthNo
dismissedNot a real problemNo
needs_reanalysisRe-check this areaYes

Your note goes to the model as untrusted data, and every resulting claim still needs verbatim code evidence. If a budget limit interrupts a re-analysis, nothing is written.

Stable IDs, versions and the changelog

Items get stable IDs such as COMP-0001 and RULE-0003 in graph/registry.json, so references survive re-analysis, and review patches persist across later analyze runs. Each analysis or resolution saves a snapshot in graph/snapshots/.

migration-agent changelog legacy-orders.migration   # writes docs/changelog.md
migration-agent audit legacy-orders.migration --format json

When the code changes

migration-agent ingest legacy-orders.migration --refresh
migration-agent analyze legacy-orders.migration --incremental --workers 4

5Docker, safety, help

Running in Docker

The image is a run-to-completion batch job: source mounted read-only, project folder read-write, non-root user 10001, read-only root filesystem, no baked-in secrets. Run the review UI on your host, not in the container.

docker build -f docker/Dockerfile --build-arg VERSION=0.2.0 -t migration-agent:0.2.0 .
docker run --rm --read-only --tmpfs /tmp --network none migration-agent:0.2.0 --version
Compose profileNetworkUse it for
offlineNoneinit, ingest, extract, render, audit, changelog, analyze --offline
modelInternal; one Squid proxy allows HTTPS to a single model hostanalyze, verify, resolve
export REPO_DIR=$PWD/legacy-orders PROJECT_DIR=$PWD/orders.migration
C="docker compose -f docker/docker-compose.yml"
$C --profile offline run --rm worker-offline init /workspace --project /project --name orders
$C --profile offline run --rm worker-offline ingest /project
$C --profile offline run --rm worker-offline extract /project
export ANTHROPIC_API_KEY=...        # or GEMINI_API_KEY; passed by name, never baked in
$C --profile model run --rm worker analyze /project --max-usd 5

The safety model

  • Source is never executed or changed. Analysis reads only the code/ copy.
  • Model tools are jailed to read_file, list_dir, grep and file_stat inside code/.
  • Secrets stay out of prompts: withheld at ingest, redacted from reports and findings.
  • Untrusted text stays data: code, user docs and reviewer notes cannot act as instructions.
  • Claims need evidence. No verifiable file, line and quote means low or no confidence and a spot in the blind-spots section.
  • Data leaves only to your configured model endpoint. Use --offline or a self-hosted gateway if that matters.
  • Keep llm_cache/ private: it holds model responses derived from your code.

Controlling cost

  1. Run analyze --dry-run and read the estimate.
  2. Set --max-usd (or MA_MAX_USD); runs stop gracefully and resume without repaying.
  3. Use gemini-lite.config.json for the cheapest runs, or a small model for chunk_extract and a stronger one for reasoning tasks.
  4. Set correct per-model prices, or estimates will be wrong.
  5. Check spend afterwards with audit.

Troubleshooting

SymptomFix
No LLM API key foundExport the key or put it in .env; or use --offline or --dry-run
macOS Operation not permittedGive your terminal access to Downloads, Desktop or Documents in System Settings, or move the project to ~/work
429, quota, RESOURCE_EXHAUSTEDUse gemini-lite.config.json, raise backoff_max, or re-run later; finished chunks are not repeated
503, model overloadedRetried automatically; if it persists the chunk is skipped and a re-run picks it up. Raise MA_LLM_MAX_RETRIES or switch model
Run stopped on budgetRaise --max-usd and re-run; completed work is reused
Many unmapped itemsCheck section 15 of docs/understanding.latest.md and exclusions in ingest_report.json
Low confidence or blind spotsRe-run with a stronger model for that task, or comment on the item and resolve
not a project folderNo project.json; run init first
